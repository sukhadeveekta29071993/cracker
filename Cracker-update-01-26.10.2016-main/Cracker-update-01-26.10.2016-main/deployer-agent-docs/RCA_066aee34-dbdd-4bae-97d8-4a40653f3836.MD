# RCA — Production admin login "not working" (sparkle-cart-9)

## Problem statement
Admin login reported failing on production (https://sparkle-cart-9.emergent.host),
POST /api/auth/login, credentials admin@crackerpos.in / admin123. Preview works.

## Conclusion
The supplied credentials (admin@crackerpos.in / admin123) are **VALID in production**.
Login is not broken. The observed 401s are caused by the **wrong email address being
entered** (typos), not by a backend, DB, CORS, seed, or hashing fault.

## Evidence
1. **Seed data present / admin exists.** Production DB `sparkle-cart-9-test_database`,
   `users` collection contains exactly one admin:
   `{email: "admin@crackerpos.in", role: "admin", approved: true, password_hash: "$2b$12$h6XSW/3mJ6DpMmTHSfq8B.HojSEOjyPoy8poqDHxzICQNV5HwHwSm"}`.
2. **Password hash matches admin123.** In an eph sandbox:
   `bcrypt.checkpw(b"admin123", <stored hash>)` → `match: True`.
   So `verify_password("admin123", stored_hash)` in the login handler would succeed.
3. **DB binding correct.** The queried DB is the live production DB — it holds real
   customer sign-ups dated 2026-10-22 … 2026-10-26.
4. **CORS fine / requests reach backend.** The backend records failed logins in
   `login_attempts`, which only happens after the request is accepted and processed.
5. **Actual failing identifiers are typos.** `login_attempts` contains:
   - `admin@crackerpod.in` (count 2)  — "pod" instead of "pos"
   - `admin@firecrackerpos.in` (count 1) — extra "fire"
   There is **no** failed/locked entry for `admin@crackerpos.in` (successful logins delete
   the record; there is no active 15-min lockout on it). Backend logs also show
   `POST /api/auth/login 200 OK`, confirming the endpoint authenticates successfully.

## Login flow (backend/server.py:367)
`email.strip().lower()` → lookup user by email → `verify_password`. Wrong email ⇒ no user ⇒
401 "Incorrect email or password". 5 failures on the SAME identifier ⇒ 429 (15-min lock).

## Secondary observation (not the current cause — latent risk)
Production secrets `ADMIN_EMAIL` and `ADMIN_PASSWORD` do NOT equal
admin@crackerpos.in / admin123 (confirmed via list_secrets matches_expected=false).
This does not affect today's login because the seed (server.py:1571) only inserts an admin
`if not await db.users.find_one({"role": "admin"})` and an admin already exists (migrated
from preview). Risk: if the admin user were ever deleted and a pod restarted, the seed would
recreate the admin using these PRODUCTION secret values — producing credentials different
from admin@crackerpos.in / admin123. Align the prod Secrets to the intended values if that
matters.

## Fixes
- **User:** Log in with the exact email `admin@crackerpos.in` (not crackerpod.in /
  firecrackerpos.in) and password `admin123`. If you recently failed 5+ times on the correct
  email, wait 15 minutes for the rate-limit lock to clear. Credentials are confirmed valid.
- **User (optional, precautionary):** Set Deployment → Secrets `ADMIN_EMAIL=admin@crackerpos.in`
  and `ADMIN_PASSWORD=admin123` to keep future re-seeds consistent with the documented creds.
